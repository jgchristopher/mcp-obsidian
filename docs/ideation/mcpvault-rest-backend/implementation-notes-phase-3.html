Implementation Notes — Phase 3

MCPVault REST Backend · 2026-07-30 · Routing, reachability, and vault fingerprint guard

Health — takes a RestClient, not a RestConfig

Context
The spec's wiring snippet reads new Health(config, resolvedVaultPath, { onWarn }), while its API sketch declares fingerprintRest(client: RestClient). The two disagree about what Health holds.
Decision
Health takes the RestClient. Building a second client from the config inside Health would open a second keep-alive agent and socket pool against the same loopback plugin, for one request every 60 seconds. createServer hoists the client into a local and hands the same instance to both RestBackend and Health.
Alternative
Follow the snippet literally and construct a client per health object, accepting the duplicate pool. Rejected: the socket cap in RestClient exists precisely to bound concurrency, and a second uncounted pool undermines it.

Plugin version floor — checked inside Health, not in server.ts

Context
The spec assigns the version-floor warning to server.ts, but createServer is synchronous and server.ts holds no REST client of its own. Reading the version there means a floating promise at startup with nothing to await it.
Decision
Health reads GET / once, on its first successful fingerprint check, and emits the warning through the same onWarn channel as a mismatch. It already owns a client and already runs on a timer, so the check costs one extra request per process. server.ts supplies the sink: process.stderr.write with an [mcpvault] tag.
Alternative
A fire-and-forget checkPluginVersion() in server.ts. Rejected: an unawaited promise that writes to stderr after startup is harder to test and can outlive a fast shutdown.

createServer — new onWarn and env options

Context
The spec's snippet hardcodes console.error inside createServer and reads process.env implicitly through resolveRestConfig(). Both make the REST wiring untestable: warnings would land in the test runner's output, and a developer shell carrying a real OBSIDIAN_API_KEY would point the suite at a live Obsidian.
Decision
Two optional options. onWarn defaults to console.error, so production behavior matches the snippet; env defaults to process.env, so config resolution is unchanged. The wiring tests inject both and drive the real MCP handlers against the phase 2 fixture.
Alternative
Mutate process.env in tests and spy on console.error. Rejected: cross-test leakage, and it still leaves the production path unable to tag its own warnings.

RoutingBackend — the unknown-state message names its target

Context
The spec's route signature carries only an operation name, but its error-handling table requires the message to name "the operation, the note, and that the state is unverified".
Decision
route takes a third argument describing what the call touches — a path, a joined path list, or oldPath -> newPath for moves. This message is the only user-facing signal for the duplicate-write hazard, so it has to say which note to go and check.
Alternative
Keep the two-argument signature and emit a generic message. Rejected: an operator told "a write may not have applied" with no path has nothing to verify.

Contract suite — three known divergences kept out of the assertions

Context
The spec requires literally identical assertions on both arms, but three behaviors legitimately differ: getNotesInfo.modified (a real mtime versus a fixture stat), listAllTags counts (occurrences versus files-per-tag, credited to hierarchical parents), and deleteNote with a non-default trashMode (REST declares it unsupported).
Decision
modified is asserted for its type only; the tag seed uses one occurrence per tag with no hierarchy, so both arithmetics agree on the same numbers; trashMode variants are covered in the routing and REST suites instead, where the unsupported path is the point. No conditional skips, no arm-specific branches.
Alternative
Assert the divergences per arm behind an if (arm.name === …). Rejected: that is a skipIf wearing a different hat, and it would let a real regression hide inside an accepted difference.

Fingerprint — dotfiles excluded on both sides

Context
The spec narrows the comparison to root-level .md filenames because PathFilter drops dotfiles while the plugin does not. PathFilter actually only drops a named deny-list, so a root note called .private.md would pass one side and possibly not the other.
Decision
reduceToFingerprint applies one normalization to both sources: drop directories, drop nested paths, drop leading-dot names, keep .md, sort. Symmetry is what matters, not which rule is chosen — an asymmetric filter is what permanently disables REST on a correct machine.
Alternative
Run each side through PathFilter. Rejected: it answers a different question (what may a tool touch) and its deny-list can grow, silently changing the fingerprint's meaning.
