Implementation Notes — Phase 4

MCPVault REST Backend · 2026-07-30 · New tools

Date resolver — local time, and tests that build dates locally

Context
The spec's smoke case is formatDate("YYYY-MM-DD", new Date("2026-07-30")) yielding 2026-07-30. An ISO date string parses as UTC midnight, so getDate() returns 29 anywhere west of Greenwich. Written literally, that assertion is a timezone-bound test — the same class of bug as the clock-bound test the spec's own Failure Modes table warns about.
Decision
formatDate reads local components (getFullYear, getMonth, getDate), because a daily note belongs to the user's day, not to UTC's. Every test builds its date with new Date(2026, 6, 30), and createServer's date argument parses YYYY-MM-DD into the same local constructor. The assertion the spec asked for still holds, in every timezone.
Alternative
UTC getters, which would make the spec's literal snippet pass. Rejected: at 8pm in Chicago that resolves tomorrow's note, which is wrong for the one user this feature exists for.

Tool count — createServer.test.ts had to be edited

Context
Contract success criterion 6 asks for no changes to the nine pre-existing test files. src/createServer.test.ts is one of them, and it asserts toHaveLength(16) plus the sorted tool-name list. The phase's whole job is registering nine more tools, so that assertion cannot survive.
Decision
Edited that one test to 25 and added the nine names, which is what the spec's own Testing Requirements table asks for ("ListTools returns 25"). No other pre-existing test file was touched; the criterion's real intent — behavior unchanged with REST off — still holds, verified by env -u OBSIDIAN_API_KEY npm test.
Alternative
Leave it and add a second file asserting 25. Rejected: the old assertion would simply fail, so this would be two contradictory tests rather than zero edits.

Fixture server — four endpoints the spec's file table omitted

Context
The spec's feedback loop for ObsidianLiveService calls for the phase 2 fixture "with /commands/, /active/, /open/, and /search/ stubbed", but src/backend/testing/fixture-server.ts is not in the Modified Files table.
Decision
Extended the fixture with those four routes plus executedCommands and openedFiles so tests can assert effects rather than only responses. POST /search/ answers 400 errorCode 40012 for any content type other than JsonLogic, mirroring what the live plugin does with Dataview absent — so a future change that sent the DQL type would fail here.
Alternative
A second, live-only fixture. Rejected: two doubles of the same plugin drift, and CI has no Obsidian to fall back on.

Periodic resolution reads local disk on the REST arm too

Context
The plugin exposes /periodic/{period}/ endpoints, so the REST arm could have resolved the daily note through Obsidian instead of reading .obsidian/daily-notes.json.
Decision
Both arms call the same loadPeriodicNote, which resolves the path from the local settings file and then reads through that arm's readNote. The read still routes; the resolution does not. A second source of truth for folder and format is exactly the drift goal 3 exists to prevent, and the plugin's periodic endpoints only answer for the periods the absent periodic-notes plugin would provide.
Alternative
GET /periodic/daily/ on the REST arm. Rejected: the contract suite would then be comparing two different resolvers, and the one that works headless is the one that must be authoritative.

open_file carries the same path guard as every other path tool

Context
ObsidianLiveService sits outside VaultBackend, so it inherits none of RestBackend's guards, and the spec does not mention filtering open_file's path. The repo's standing rule (AGENTS.md) is that pathFilter.isAllowed plus normalization must guard every new tool's path input — the exact blocker that stopped PR #146.
Decision
open_file normalizes, rejects traversal, and runs PathFilter before any request leaves the process. This is the third copy of that guard (FileSystemService, RestBackend, here); it is deliberately the smallest of the three, and extracting all three is left for whoever next has a reason to touch filesystem.ts's copy.
Alternative
Rely on the plugin to refuse. Rejected: a tool that can surface .obsidian/* in the UI is a hole in a boundary this project keeps closed everywhere else, and the plugin's behavior is not ours to depend on.

The five REST-only tools are not gated by the vault fingerprint

Context
Health refuses REST when Obsidian holds a different vault than vaultPath. ObsidianLiveService sits outside the seam, so no such gate applies to it.
Decision
Left ungated, as the spec specifies. list_commands, execute_command, and get_active_file are app-global rather than vault-relative, so gating them on vault identity would refuse correct calls. The one vault-relative member, open_file, performs a UI navigation with no write.
Alternative
Inject HealthGate and gate open_file. Not rejected on merit — deferred, because it needs the live parity pass in phase 5 to say whether a mismatched-vault open_file is confusing enough to be worth the coupling.

A malformed daily-notes.json throws instead of reading as "unconfigured"

Context
The spec covers exactly two cases for the config reader: present, and missing (null). It says nothing about a file that exists but is unparseable.
Decision
Missing returns null as specified. Unreadable or malformed throws, naming the path. Reporting a broken settings file as "daily notes are not configured" would send the user to enable a plugin that is already enabled.
Alternative
Return null for anything that fails to parse. Rejected: it collapses two very different faults into one misleading message.

Module path — src/backend/periodic, not src/backend/filesystem/periodic

Context
The contract's success criterion 3 checks npm test -- src/backend/filesystem/periodic, while the phase spec's File Changes table puts every periodic file under src/backend/periodic/.
Decision
Followed the spec. The resolver is shared by both arms — the REST backend imports it too — so filing it under filesystem/ would say the wrong thing about ownership. Phase 5's verification should run npm test -- src/backend/periodic.
Alternative
Match the contract's path so the check command runs verbatim. Rejected: the directory name would be actively misleading, and the criterion's substance (config-derived resolution, proven by changing the fixture config) is asserted either way.
