Implementation Notes — Phase 5

MCPVault REST Backend · 2026-07-30 · Parity verification and cutover

Live smoke script — the reachability guard was not sufficient

Context
The spec says the script should refuse to run when OBSIDIAN_API_KEY is unset or GET / is unreachable, and lists "false pass from the filesystem" as a failure mode the guard prevents. It does not prevent it. A reachable Obsidian holding a different vault answers GET / happily, at which point Health.restUsable() returns false and every routed tool is quietly served from disk while the guard reports green.
Decision
The preflight also compares fingerprintRest(client) against fingerprintFilesystem(vaultPath) and refuses on mismatch, printing both root listings. Both helpers were already exported standalone from src/backend/health.ts, so this reuses the guard the routing layer uses rather than inventing a second notion of vault identity.
Alternative
Implement the spec literally and accept that the one failure mode the smoke run exists to rule out could pass silently. Rejected: the whole point of the run is to justify deleting the old server.

Live smoke script — auth failure was being reported as "start Obsidian"

Context
fingerprintRest throws for two unrelated reasons: a BackendError when the request never got an answer, and a plain Error when the server answered with a non-2xx. Collapsing both into one message told anyone with a stale key to start an Obsidian that was already running.
Decision
Branch on err instanceof BackendError. Transport failures say start Obsidian and name the 27123 port trap; HTTP failures say the server answered and refused, and point at the key. Both branches were exercised manually — a bogus key produces the auth message, and port 27124 produces the connection-refused message.
Alternative
Print the raw error and let the reader work it out. Rejected: a 401 reads as a network problem to most people.

Live smoke script — an absent daily note counts as a pass

Context
The spec does not say what get_periodic_note should assert. src/backend/periodic/resolve.ts returns exists: false for a correctly resolved path whose file has not been created yet, which is a correct answer, not a failure.
Decision
The check passes on any resolved response and labels whether the note existed. Requiring the file to exist would fail the whole run on any day the daily note had not been touched yet, which is most mornings.
Alternative
Create the daily note first. Rejected: the run would write to a real note outside its scratch folder.

Live smoke script — resolved promises are not passes

Context
createServer catches every handler throw and returns { isError: true } rather than rejecting. Several tools additionally report failure as success: false inside a resolved, non-error response.
Decision
The shared call() helper checks isError and then parses the body for an explicit success: false. Treating resolution as a pass would have printed thirteen greens against a server whose every handler was broken — precisely the evidence the cutover decision rests on.
Alternative
Rely on await throwing. Rejected: it never throws here.

Parity table — 13 rows, 11 distinct targets

Context
The spec asks the test to assert "the count is exactly 13". Thirteen is the row count; list_directory and write_note each answer two Python tools, so only eleven distinct MCPVault tools are referenced.
Decision
Separate assertions: length === 13, thirteen unique python names, and eleven unique mcpvault targets. An added test documents the 11 explicitly so a future reader does not "fix" it to 13.
Alternative
Assert 13 distinct targets, which fails immediately and misleadingly.

README — two adjacent claims were false before this phase

Context
The spec scopes the README to the REST backend, the env vars, the port trap, and the version floor. The Features list immediately above that content said "14 methods" (the server registers 25) and "Zero dependencies: No Obsidian plugins required", which the new section directly contradicts.
Decision
Corrected both. Leaving them would have produced a document that contradicts itself within one screen. The tool count was updated to 25 with the new groups listed, and the zero-dependencies bullet was reworded to say the core tools need no plugin while naming the optional REST backend.
Alternative
Stay strictly inside the spec's scope and flag the contradictions in the report. Rejected for these two because they sit in the same list as the new content; other stale spots found by the scout were left alone and are listed in the completion report.

Scripts are outside every tsconfig

Context
Neither tsconfig.json nor tsconfig.build.json includes scripts/, and CI never compiles it. A type error in either new script would ship and only surface when someone ran it.
Decision
Both scripts were typechecked against the project's strict settings via a temporary config, which passed clean, and the temporary config was removed. The permanent fix — adding "scripts/**/*" to tsconfig.json's include — was not made, because it is outside this spec's File Changes and would subject the directory to noUnusedLocals and exactOptionalPropertyTypes as a side effect of a parity phase.
Alternative
Expand the tsconfig now. Deferred to a follow-up so the change is deliberate rather than incidental.

A third script file was added

Context
The spec's File Changes table lists two scripts. Review found that the benchmark constructed RestBackend with no vault-identity guard, so a REST arm bound to a different vault would write eighteen bench notes into that vault while the filesystem arm wrote to this one, and the printed table would compare two vaults as one.
Decision
The guard moved to scripts/preflight.ts and both scripts import it. Phase 2 already flagged duplicated path logic as a smell; copying a twenty-line safety check into a second file would repeat that mistake in the one place where getting it wrong writes to the wrong vault.
Alternative
Duplicate the guard, or export it from src/backend/health.ts. The first repeats a known smell; the second modifies a phase-3 file for a phase-5 need.

Two notes are seeded, not one

Context
The two cross-arm checks assert that a REST-written note is visible to a filesystem read, which is the run's strongest evidence that both arms address one vault. But get_recent_changes is row 13 and obsidian_delete_file is row 10, so a single scratch note would be asserted present three checks after the run deleted it.
Decision
SCRATCH_NOTE is the mutable subject that the write, patch, append, and delete checks operate on. PERSIST_NOTE is seeded alongside it, touched by no check, and removed only in teardown; both cross-arm checks assert against it. Both are written through the client so both are REST writes when REST is serving — a filesystem seed would make the cross-arm assertion prove nothing.
Alternative
Drive the loop from a hand-ordered list instead of the table. Rejected: the table is the source of what must be covered, and a parallel ordering list is a second thing to keep in sync.

Not every warning should fail the gate

Context
Treating any warning as fatal was the first fix for "REST degraded mid-run goes undetected". Review showed it both over- and under-fires. checkPluginVersionOnce pushes the version-floor warning into the same array, so a healthy run against a 4.1.6 plugin would fail the cutover gate for a condition the README documents as warn-and-continue. And Health deliberately does not warn when the fingerprint request fails with a BackendError, so quitting Obsidian mid-run left the array empty and the gate green.
Decision
Warnings are partitioned on the Vault fingerprint prefix: those fail the run, everything else prints as a note. Separately, the fingerprint is re-checked against the preflight client after the loop, which is what actually closes the window between preflight and the last assertion.
Alternative
Match on exact warning strings. Rejected as brittle against a reworded message in health.ts.

The scratch folder was never being removed

Context
Both scripts cleaned up with rm(dir, { recursive: false }) under a .catch(() => {}). That call throws ERR_FS_EISDIR on a directory unconditionally — verified directly — so the catch swallowed it and MCPVault_Parity_Smoke/ would have accumulated as an empty folder in the vault after every run, which is exactly what the comment above the line claimed to prevent.
Decision
rmdir() in both scripts. It removes an empty directory and fails ENOTEMPTY if something unexpected is inside, which is a better signal than recursive: true quietly deleting it.
Alternative
rm(dir, { recursive: true }). Rejected: it would delete a non-empty directory without complaint, in a real vault.

The scripts were driven against the in-repo fixture

Context
Review's central objection to cycle 1 was that none of its four defects would have survived a single live run, and no live run was possible without the API key.
Decision
Both scripts were run end to end against src/backend/testing/fixture-server.ts over HTTP, pointed at a mkdtemp vault with a matching root note and a .obsidian/daily-notes.json. The smoke run reaches 11/13 with a correct exit code and no hang; the benchmark completes and its on-disk teardown was confirmed to leave the vault root clean, which is how the EISDIR defect was caught.
Alternative
Ship on the mapping test alone. Rejected: it would have shipped four defects. The harness's limit is that the fixture's in-memory store and the temp vault are separate, so the two cross-arm checks cannot pass there — they are expected to pass live, and that remains the one assertion no run so far has verified.

The cutover was not performed

Context
Steps 1–7 of the spec's cutover edit ~/.claude.json, delete the obsidian-jcos entry, and require a live smoke run first. The user had already decided to keep that edit under their own hand, and the permission layer blocked reading OBSIDIAN_API_KEY out of the config, so the live smoke could not run in this session either.
Decision
Everything mechanically verifiable was built and validated; the live smoke, the benchmark, and the config edit are left as documented manual steps. Both scripts were exercised through their refusal paths, which is the half that can be tested without the key.
Alternative
Extract the key another way and complete the cutover. Rejected: it works around a denial rather than respecting it, and the user's standing instruction was explicit.
