The problem

01John runs two overlapping MCP servers against the same Obsidian vault. obsidian-jcos is the Python mcp-obsidian pinned to commit 4aac5c2, reaching the vault over the Local REST API plugin. MCPVault reaches vaults over the filesystem. Together they present roughly 29 tools, many of which do the same thing by different routes.

02Each server can do something the other cannot, so neither can be dropped. MCPVault has no access to anything that only exists inside a running Obsidian: periodic note resolution, registered commands, the active file, or link-preserving moves. The Python server has that access but cannot work when Obsidian is closed, and one of its tools is already broken here. obsidian_get_recent_changes issues a Dataview DQL query, and the Dataview plugin is not installed in the jcOS vault, so that request returns 400 errorCode 40012 today.

03A naive merge of the two approaches introduces a data-integrity hazard that neither server has alone. The Local REST API binds to whichever vault Obsidian currently has open, which is jcOS, confirmed by comparing its root listing against the filesystem. MCPVault binds to its vaultPath argument. Nothing connects the two, and the plugin exposes no vault identity on its status endpoint. A server launched against one vault while Obsidian holds another would read and write different vaults depending only on whether the app happened to be running, and write_note would land content in the wrong vault with no error. Because Obsidian is almost always open here, a guard that only revalidates after a connection failure would effectively never run, so the check must be time-based rather than failure-triggered.

Goals ×7
01 Remove the obsidian-jcos entry from ~/.claude.json with no capability lost: all 13 of its tools have a working MCPVault equivalent verified against the live jcOS vault.
02 Every routed tool returns equivalent observable results whether REST or the filesystem served it, enforced by a shared contract suite that runs both arms in CI without a live Obsidian.
03 Daily note resolution works with Obsidian closed, deriving folder and format from Obsidian's own daily-notes configuration so the two cannot drift apart.
04 A REST backend bound to a different vault than the server's vaultPath can never serve a request, including a vault switch that happens while Obsidian stays running and no connection ever fails.
05 With OBSIDIAN_API_KEY unset, behavior is unchanged from today: the existing test suite passes without a single test file being edited.
06 A write whose outcome is unknown because Obsidian became unreachable mid-request never re-applies against the filesystem.
07 Capabilities that exist only inside a running Obsidian become reachable from MCPVault: registered commands, the active file, opening a note in the UI, and Obsidian's own query index.

MVP — must ship ×19
  • VaultBackend interface with a three-variant BackendFailure taxonomy— Routing switches on exactly three cases (never-sent, unknown-state, unsupported-by-this-backend); capping the taxonomy stops variants accumulating that no branch reads
  • FileSystemBackend as an adapter over the existing FileSystemService— Adapting rather than rewriting keeps the 110 existing filesystem tests valid and untouched
  • RestClient built on node:https with a scoped Agent— Node's global fetch ignores an https.Agent, so TLS relaxation cannot be scoped through it; node:https gives agent control with no new dependency
  • In-repo REST test double (node:http fixture server)— The repo has no HTTP client and no mocking library, and CI runs on ubuntu with no Obsidian; without a double the REST arm of the contract suite cannot run in CI at all
  • RestBackend for the 13 routed tools: read_note, read_multiple_notes, get_notes_info, write_note, patch_note, delete_note, move_note, move_file, list_directory, get_frontmatter, update_frontmatter, manage_tags, list_all_tags— Each is either path-scoped or has a direct single-call endpoint where REST observably differs: richer note payloads, structural heading and block patching, link-preserving MOVE, and GET /tags/ backed by Obsidian's index
  • search_notes, get_vault_stats, and wiki_link stay filesystem-only— search_notes would change result sets based on whether Obsidian is open; the other two are whole-vault derivations that REST could only serve as N calls re-deriving an identical answer
  • Vault fingerprint guard with time-based revalidation— Compares the sorted set of root-level .md filenames from GET /vault/ against readdir, which is comparable across both sources unlike full listings; revalidating on a TTL rather than on connection recovery is the only way the guard fires on an always-open Obsidian
  • Reachability flag rather than a half-open circuit breaker— Obsidian closed means an immediate ECONNREFUSED on localhost, so a boolean plus a last-checked timestamp covers it without timing windows or a constant nobody tunes
  • Five-variable configuration with explicit defaults and a documented plugin version floor— This vault serves HTTPS on 27123 with the insecure server disabled, inverting the usual convention, so a baked-in 27124 default would fail silently into permanent fallback; BRAT is installed so plugin versions move on their own
  • Shared backend contract test suite— Load-bearing precisely because Obsidian is almost always open, so the filesystem branch would otherwise go untested until the one outage that needs it
  • get_periodic_note, routed, with the config reader bypassing PathFilter entirely— Reading daily-notes.json through a hardcoded relative path inside the resolver leaves PathFilter and its 51 tests untouched, instead of adding an allowlist mechanism to a deliberately closed boundary
  • Date resolution limited to YYYY, MM, and DD with a named error on any other token— Only daily is reachable, and the live format uses only those tokens; an unsupported format must fail loudly rather than silently resolve a wrong path
  • get_document_map, routed— Derived from the note payload REST already returns, so routing it costs one mapping rather than a second fetch
  • get_recent_changes, filesystem-native, reusing the existing vault scan— FileSystemService already walks and sorts by mtime for get_vault_stats; this adds a days filter and a higher cap rather than a second walker, and fixes a tool that is broken in this vault today
  • get_recent_periodic_notes, filesystem-native— Closes the last parity gap against obsidian-jcos and works headless
  • list_commands, execute_command, get_active_file, open_file, search_vault_advanced— Delivers goal 7; each has no filesystem equivalent and fails closed with a clear error when Obsidian is unreachable
  • Parity mapping test and live smoke script— Retirement of obsidian-jcos was made conditional on parity, so parity needs a check rather than a feeling
  • Backend benchmark script— Gives visibility into REST versus filesystem cost on the hot path without putting a wall-clock assertion into CI
  • Cut ~/.claude.json over to the local build, carrying the five OBSIDIAN_ values across before deleting obsidian-jcos— That entry is the only place those values live, so deleting it first would lose the API key
Out of scope — said no on purpose
  • Using the plugin's own /mcp endpoint as the transport — REST has a stable OpenAPI spec, returns richer note payloads in one response, and needs no session handshake; the MCP endpoint offers no capability REST lacks
  • Dataview DQL queries in search_vault_advanced — The Dataview plugin is not installed in jcOS; the endpoint returns 400 errorCode 40012, so advertising it would ship a broken path
  • Weekly, monthly, quarterly, and yearly periodic note resolution — The periodic-notes community plugin is absent, so weekly returns 404 and the rest return 400; the tool accepts all five periods but only daily can work today
  • Multi-vault support beyond jcOS — Obsidian serves one vault at a time, so a second instance would be filesystem-only anyway; scoping to jcOS keeps the fingerprint guard simple
  • Routing search_notes, get_vault_stats, or wiki_link through REST — One would change result sets based on whether the app is open; the other two are whole-vault walks REST could only serve as N calls for an identical answer
  • p95 latency assertions in the test suite — This repo already tuned a wall-clock test from 100ms to 200ms for CI stability and then deleted it; a benchmark script gives the visibility without the flake
  • npm publishing under a personal scope — The config points at a local build path, so publishing adds a release step per change with no benefit at one machine
  • Upstream contribution to bitbonsai/mcpvault — Explicitly chosen as a fork-local feature branch
Future — someday, maybe
  • Install the periodic-notes plugin to unlock weekly, monthly, quarterly, and yearly resolution, which the tool already accepts
  • Install Dataview to unlock DQL queries in search_vault_advanced and richer recent-changes queries
  • Extract a shared test-helper module; the mkdtemp setup block is currently duplicated in every stateful test file
  • Revisit upstream contribution if the backend seam proves stable and rebases stay cheap

## Phase Kind Risk Notes
01 Backend seam and filesystem adapter phase · blocking low Define the VaultBackend interface and the three-variant BackendFailure taxonomy, then adapt the existing FileSystemService behind it and switch the tool handlers in createServer.ts to call the backend. The existing suite is a weak regression check here: only 15 of 245 tests go through createServer, and the 110 filesystem tests construct the service directly, so this phase adds handler-level tests through createServer for every routed operation.
02 REST client, backend, and test double phase · blocking med Greenfield HTTP on node:https with a scoped Agent, auth, and the classification separating never-sent from unknown-state failures. RestBackend maps the 13 routed operations onto REST endpoints including the WebDAV-style MOVE verb. Ships the node:http fixture server that lets the REST arm run in CI, which phase 3 depends on.
03 Routing, reachability, and vault fingerprint guard phase · blocking high The phase that can corrupt data if wrong. REST-preferred routing, the read and write fallback asymmetry, the reachability flag, and the fingerprint comparison on root-level .md filenames with TTL revalidation so a vault switch is caught while Obsidian stays up. The shared contract suite lands here and runs both arms against the fixture server.
04 New tools phase low Nine additive tools on a proven seam: two routed (get_periodic_note, get_document_map), two filesystem-native reusing the existing vault scan (get_recent_changes, get_recent_periodic_notes), five REST-only. Includes the YYYY/MM/DD resolver and the config reader that bypasses PathFilter with a hardcoded path.
05 Parity verification and cutover gate · blocking med Human checkpoint requiring a running Obsidian on jcOS. Parity mapping test, live smoke across all 13 equivalents, benchmark run, then copy the five OBSIDIAN_ values into a new mcpvault entry, confirm one live REST call succeeds, and only then delete obsidian-jcos.
