Implementation Notes — Phase 1

MCPVault REST Backend · 2026-07-30 · Backend seam and filesystem adapter

VaultBackend interface — four signatures do not match FileSystemService

Context
The spec's Open Items say "None. All interface members map to existing FileSystemService methods." Four do not. writeNote and updateFrontmatter return Promise<void> in the service, not { success, path, message }. listAllTags returns { tag, count }, not { name, count }. And there is no getFrontmatter method at all.
Decision
The interface was written to match the service. Contract goal 5 forbids editing any pre-existing test file, and the filesystem behavior is what phase 3's contract suite holds both backends to, so the filesystem shapes are authoritative. The spec also demands deep-equality tests between the adapter and the raw service, which is only satisfiable if the adapter returns the service result unchanged. Phase 2's REST backend maps GET /tags/'s { name, count } onto { tag, count } on its side.
Alternative
Keep the spec's literal signatures and have the adapter synthesize result objects and rename tag keys. Rejected: that is translation, it breaks the deep-equality check the spec asks for, and the { name, count } shape would change list_all_tags output for every existing caller.

FileSystemBackend.getFrontmatter — the one method with logic in it

Context
getFrontmatter is in the routed set and in the interface, but FileSystemService has no such method. The get_frontmatter handler previously called readNote(path).frontmatter inline.
Decision
The adapter reproduces exactly that: read the note, return its frontmatter. The projection moved from the handler into the adapter, so the observable response is unchanged and phase 2 can serve the same operation from one REST call.
Alternative
Leave get_frontmatter unrouted. Rejected: the spec and the contract both list it among the 13 routed tools, and phase 2 maps it to GET /vault/{path}.

Handler tests live in a new file, not in createServer.test.ts

Context
The spec's File Changes table says to add the handler-level tests to src/createServer.test.ts. Its own Validation Commands then require git diff --stat main -- 'src/**/*.test.ts' to show no changes to the nine pre-existing test files, which contract goal 5 also demands. Both cannot hold.
Decision
The tests went into a new file, src/createServer.routing.test.ts. It is picked up by the vitest src/**/*.test.ts include and by the spec's own check command npm test -- src/createServer, so the coverage deliverable lands while the no-edit gate stays clean.
Alternative
Edit createServer.test.ts and accept the gate failure. Rejected: the gate is a hard, machine-checked contract criterion; the file name is not.

CreateServerOptions.backend is typed VaultBackend | undefined

Context
The spec's snippet declares backend?: VaultBackend, while its Error Handling table requires a caller passing backend: undefined to land on the default. The repo compiles with exactOptionalPropertyTypes: true, so the optional-only form makes the documented call a type error.
Decision
Declared backend?: VaultBackend | undefined, with a test asserting the explicit-undefined call still writes through the default adapter.
Alternative
Keep the narrow type and cast in the test. Rejected: that hides the contradiction rather than resolving it, and phase 3 builds the backend conditionally.

src/index.ts re-exports the backend types

Context
The spec's File Changes table lists only createServer.ts as modified. But CreateServerOptions is exported from the package entry and now has a backend member typed VaultBackend, and the package exports map exposes only ".", so a consumer could not name that type.
Decision
Added VaultBackend, BackendFailure, BackendError, and FileSystemBackend to src/index.ts. Purely additive and inert at runtime.
Alternative
Leave the entry point alone and let consumers deep-import dist/src/backend/types.js. Rejected: the exports map blocks it.

Review ran as validation-only

Context
execute-spec calls for an ideation:reviewer subagent pass before commit. No agent-dispatch tool was available in this execution environment.
Decision
Fell back to the skill's documented validation-only mode: full typecheck including test files, the full 309-test suite, npm run build, and a deliberate mutation check that reverted two routed cases to fileSystem and confirmed the new tests fail. A human reviewer pass is still worth running on this diff.
Alternative
Skip the commit until a reviewer is available. Rejected: the phase is behaviorally inert and fully revertible, and blocking here stalls the whole chain.
